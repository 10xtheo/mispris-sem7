## Порядок работы через Swagger

1. Создать класс, изделие и его базовую единицу существующими API справочников.
2. Создать параметры через `/api/parameters`, используя типы перечисления `param_type` (`number`, `string`, `enum`).
3. Назначить параметры классу: POST `/api/configuration/classes/{class_id}/parameters`.
4. Включить конфигуратор: PUT `/api/configuration/items/{item_id}/configurator`.
5. Описать функции, добавить ограничения шаблона; проверить комбинацию через `/check`.
6. Создать вариант через `/variants` с обозначением, названием и `values` по кодам параметров.
7. Зарегистрировать заказ, добавить вариант в позиции, получить документ состава, согласовать.

Примеры выражений приведены в `tests/unit/test_constraint_interpreter.py`, сквозной рабочий пример — в `tests/e2e/test_lab7_scenarios.py`.

## Проектные решения и границы каркаса

Функции, классы функций, операторы, формальные аргументы, константы, вызовы, фактические аргументы и корни ограничений хранятся в связанных таблицах миграции 005. JSON используется для передачи запросов; поля definition/expression с хранимыми деревьями удалены. Интерпретатор читает нормализованные записи.
- Представления заказа: JSON и HTML для печати/сохранения в PDF.
- Калькуляция использует маршруты конкретных изделий через №6; отсутствие маршрута диагностируется. Каждая позиция — отдельная партия.
- Назначения параметров можно менять/удалять до появления вариантов; опубликованная модель защищена от изменения этими операциями.
- Библиотека функций после создания доступна для чтения, визуальный редактор деревьев не входит в каркас.
